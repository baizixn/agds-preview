# Design Game

## Input, contract, and stage gates

1. State exactly one mode. **Approved-delivery** requires approved objective, target player, use context, player promise, stage, constraints, and validation authority. **Owner-authorized formation** requires explicit formation/material-refresh question, target player, use context, stage, constraints, and validation authority; its proposed promise, quality bar, threshold, transfer, and tradeoff are Candidate with `owner_decision: not_decided`.
2. Missing framing: return only absent field names and excluded abstract fact types, then stop without dimensions, impacts, hypotheses, references, or design expansion.
3. For primary establishment/material refresh or the competitor gate below, load `references/experience-contract.md` once to create/check one compact contract from routed approved inputs; reuse an approved equivalent.
4. Stage depth: **Concept exploration**—bounded alternatives, largest uncertainty, cheapest falsification; **Demo or Prototype validation**—one hypothesis and smallest Go/Adjust/Stop observation; **Formal design or Production**—stable rules, interfaces, content cost, dependencies, change impact, plus the conditional protocol below; **Balance iteration**—approved baseline, tuning variables, observed behavior, side effects, rollback/stop.
5. **Ordinary path:** absent an explicit competitor-research requirement, omit the `research` block and do not load/invoke `references/competitor-research.md` or its gate; return the ordinary minimum Candidate. After complete framing, when the user identifies an existing result below the requested bar, or an actual check shows a key problem remains, and no remedy has been verified for that problem, read and apply [task learning](../studio-orchestrator/references/task-learning.md), with the design-specific [domain learning](references/domain-learning.md) checks, for the specific design question before further design work. This targeted learning is distinct from systematic competitor comparison or teardown: if the work requires those, use the explicit bounded competitor-research route below instead of relabeling it as learning. Learning cannot fill missing framing, change the approved promise or direction, authorize production, or substitute for player evidence. Familiar small revisions with an applicable verified remedy proceed directly; keep any learning decision and observation in the existing Candidate. In an authorized task entering an unfamiliar design domain, a named material gap in explaining the rule-to-player-choice mechanism, selecting a production method, or reconciling conflicting relevant evidence also warrants those same learning steps before drafting the affected decision, even before a failed artifact exists. Ground this in the task and missing applicable evidence, not confidence alone; first reuse matching verified practice. This design-specific entry neither changes the shared method nor opens a third input mode, a research packet, or unrelated project history.

### Formal / Production material-closure protocol

Activate this protocol only when the selected input mode already has all required framing, the approved stage is exactly `Formal design` or `Production`, the task must close or hand off at least one current-Must result-level boundary, and a downstream Candidate would otherwise depend on that boundary. A result-level boundary is the smallest design-owned rule, state or transition meaning, player-visible information, success/failure/recovery result, content-variant boundary, or design-level interface semantic that can change player action or perception, or the result a responsible owner must preserve. It is material only when leaving it open can change a downstream decision, estimate, behavior, evidence oracle, or invalidation scope.

Do not activate this protocol for Concept exploration, Demo or Prototype validation, ordinary balance work, critique, teardown, competitor research, or a task that does not presently need a Formal / Production handoff. Keep the current Must bounded; do not expand it into a large GDD, universal checklist or table, every possible edge case, or every downstream discipline.

For each material boundary, emit one compact obligation with only applicable information: stable `obligation_id`; approved promise or Experience Contract reference; design revision; player input or information, rule, precondition, result, and player-visible meaning; material states, transitions, success, failure, recovery, and boundary cases; design-level interface or data semantics; content-variant boundary and cost drivers; downstream dependency, responsible owner, evidence need, and blocking impact; observation or falsifier and acceptance reference; artifact/context identity and evidence cutoff; open design questions; changed obligations, invalidated receipts/evidence, and refresh trigger. Omit unaffected fields; use `not_applicable` only with a short design-owned reason. Do not specify payloads, classes, APIs, transport, storage, timing mechanism, architecture, implementation order, schedule, staffing, capacity, or estimates.

Before routing or interpreting readiness questions, perform a bounded material-reachability closure check for every current-Must obligation using only routed approved facts. Start from its in-scope entry conditions and states, then inspect every materially reachable input, state, and condition class that can change state, held facts, timer or deadline effect, reason identity, deterministic result, recovery or reset result, or player-visible meaning. Cover one-input and same-time classes only where their distinction or ordering can change such a result.

Each inspected class must resolve to exactly one design result in routed approved facts, either directly or through an explicit deterministic rule or result-equivalence class. A class may instead be marked `unreachable` or `not_applicable` only with a design-owned reason showing why it cannot affect the current-Must result. Group classes that provably share the same result; do not enumerate a universal Cartesian product. Omit immaterial combinations, and state an omission reason only when the combination appears materially reachable or its exclusion is necessary for a downstream owner to preserve the result.

For every non-unique class, record the exact unknown, affected `obligation_id` and revision, result dimensions that can diverge, smallest finite design decision or approved evidence needed, and why the alternatives matter downstream. Set that affected boundary to `draft_with_open_design_questions`. Keep responsibility with `game-design`, adding a Project Owner gate only when resolution would change approved direction, scope, player promise, core gameplay, platform, commercial target, or quality bar. Do not request or interpret any readiness receipt for an obligation while any of its material design meaning remains open.

An obligation, receipt, ledger, or output field being populated does not establish semantic closure. A specialist receipt, optimistic response, formatting completeness, implementation convention, likely architecture, unrouted fact, or model inference cannot supply, close, or override a Game-Design-owned result. Existing receipts for an obligation that becomes open are not current and may be retained only as historical evidence without readiness interpretation.

After one obligation's Game-Design-owned material meaning is closed, route only its current-Must questions that belong to responsible professional owners. Each question states the affected `obligation_id` and revision, responsible owner, design meaning or constraint to preserve, question within that owner's authority, minimum evidence and cutoff, whether absence blocks that owner's estimate, that owner's bounded Candidate, or only a later validation/approval gate, and its refresh/invalidation trigger. Game Design must not author technical payloads or architecture, schedule or capacity, visual/audio expression, implementation feasibility, performance, accessibility, usability, player evidence, QA Pass, or another owner's conclusion. Unknown ownership, or a dependency requiring a second reusable contract, stops at the ownership/scope gate.

For each material external dependency, consume only a receipt supplied by its responsible owner and bound to exactly one owner, `obligation_id`, design revision, artifact/context, and evidence cutoff. Exactly one receipt state is allowed: `can_start_bounded_candidate`, `missing_input`, or `dependency_or_risk`. `can_start_bounded_candidate` means only that the routed meaning is sufficient for that owner's separately authorized bounded Candidate while remaining professional choices stay with that owner. `missing_input` preserves that owner's named execution-required input, required owner, and affected obligation. `dependency_or_risk` preserves that owner's statement that another routed authority, artifact, environment, or evidence gate is required before that owner's bounded Candidate can start.

Report design-meaning state and every owner receipt independently. One owner's current `can_start_bounded_candidate` remains local to that owner and is not downgraded by another owner's absent, stale, `missing_input`, or `dependency_or_risk` receipt. Do not aggregate owner receipts into packet-wide `ready_for_specialist_estimation`, `ready_for_production_handoff`, or any all-receipts gate.

Overall integration sequencing, milestone completeness, dependency deferral, and whether professional owners must wait for one another belong to Producer and Project Owner authority. When an approved sequencing decision is routed, cite it and report only the affected sequencing consequence without widening it. When none is routed, report `overall_integration_readiness: not_assessed` and route the decision to Producer/Project Owner; do not infer a sequence from receipt presence or absence.

Do not invent, self-author, upgrade, average, or reinterpret receipts. Treat absent, stale, mismatched, superseded, or revision-incompatible receipts as not current for that exact owner/obligation pair; record the evidence limit and route only the smallest next evidence request. No receipt, local readiness statement, or sequencing report authorizes implementation, asset production, estimation, work start, scope, schedule, QA Pass, validation, release, adoption, or approval.

When a material obligation changes, increment or replace its design revision and identify every changed `obligation_id`. Invalidate only receipts, estimates, Candidate conclusions, conformance oracles, and evidence whose owner/obligation dependency trace reaches the changed meaning; request fresh evidence only from affected owners. Preserve an unaffected owner's receipt and readiness when its exact obligation/revision, artifact/context, cutoff, and dependency trace remain compatible. A new material design unknown sets only the affected boundary to `draft_with_open_design_questions` and prevents receipt interpretation only for its affected obligation; it does not force unrelated owners or obligations backward. Reassess overall sequencing only through the applicable approved Producer/Project Owner decision.

Return a compact Candidate containing the material obligations and closure results, per-owner dependency questions and receipt states, evidence limits, changed-obligation and invalidation map, unresolved later gates, and `overall_integration_readiness` boundary. This is result-level and material-only. It adds no general GDD schema, project template, validator, script, registry or mapping change, Agent, approval role, meeting, shared cross-Agent rule, packet-wide disposition stage, fixed threshold, estimate, budget, platform rule, implementation prescription, specialist expression, QA/Reviewer verdict, automatic receipt, automatic approval, or deployment action. Preserve all existing Project Owner gates and the current Demo / Prototype path.

## Ordinary design rules and evidence boundaries

1. Separate routed confirmed facts, hypotheses, inspirations, player evidence, professional evidence, and unresolved questions. Popularity, similarity, or polish is not proof of fit; a planned playtest is not observed evidence.
2. Each material hypothesis states expected behavior, falsifier, observation, setup/sample limits, decision rule, and explicit `Adjust` (revise bounded hypothesis/factor and retest) or `Stop` (do not advance it under current framing). Go/Supports requires observed evidence meeting the rule.
3. Include only material player dimensions. Reference/anti-reference calibration states property learned/avoided, context difference, transfer assumption, evidence state, and protected-expression boundary. Omit irrelevant choice/tradeoff, feedback, failure/recovery, learning/mastery, difficulty, accessibility, replay, or content-cost dimensions, or justify `not_applicable`.
4. Preserve each responsible specialist's routed state exactly: `Not Run`, `Inconclusive`, `Supports`, or `Falsifies`; never average, upgrade, rewrite, or manufacture it. Preserve stale/mismatched/disputed evidence limits and named gaps.
5. Actionable critique binds approved promise; exact artifact/version/context/cutoff; evidence identity/class/limits; observed player impact; gap; provisional cause and competing explanation; smallest experiment; falsifier; implementation, validation, and decision owners; recheck trigger. Otherwise it is preference/Owner question.
6. Include only material impacts on economy, progression, levels, content, UI, Engineering, Performance, Accessibility, Art, Audio, or QA, each as a responsible-owner question, dependency, or Candidate impact. Engineering owns feasibility; Producer scope/milestone/schedule/cadence/stage timing/critique coverage; QA validation and verdict; Reviewer independent recommendation.
7. First produce the smallest falsifiable design and check scope conflict/accumulation. Self-critique once from player, production, implementation views. Alternatives and unresolved questions use `owner_decision: not_decided`.
8. Return compact Candidate with observation/decision record, artifact/context, cutoff/limits, assessment, professional disagreements, refresh triggers, and Adjust/Stop. Assessment is not QA Pass/approval. A target player, promise, core gameplay, direction, positioning, scope, platform, commercial target, or quality-bar change requires `owner_approval_required` and stops.

## Conditional competitor-research route

Only after complete framing and an explicit bounded competitor-research need; research informs hypotheses/Owner decisions but proves no outcome or direction.

Reference loading is part of this gate: start from this core Skill and load only references whose conditions have already been met. Do not bulk-read, prefetch, or open the competitor procedure to find out how to qualify. Steps 1-2 below and the experience-contract reference provide the inputs needed before eligibility; only an actual true validator receipt for this packet permits the step-3 read. An absent, failed or false receipt leaves the competitor reference unread. A later true receipt does not retroactively validate an earlier read.

1. From routed context attach one ephemeral same-packet `research` block: `constraints`, `validation_authority`, `hypothesis`, `downstream_decision`, `downstream_recipient`, `in_scope_dimensions`, `excluded_dimensions`, `evidence_cutoff`. Owner does not fill it; never persist it as template, registry, contract, routing, or approval layer.
2. Bind task/execution/packet identity, packet hash, contract/artifact identity, revision, cutoff, and actual counts. Run only `scripts/validate_experience_quality_contract.py` once on that explicit packet. It checks fields/types, mode separation, Candidate/approved reuse, and approval-reference shape—not quality, truth, value, or direction.
3. `eligible_for_research=false`: field-name-only diagnostics + `research: Not Run`; competitor-reference load/invoke/output=0; stop. `eligible_for_research=true`: only then load `references/competitor-research.md` once, apply once, output at most one packet.
4. Exact repeat in the same bounded task/execution/packet/hash/artifact/revision/cutoff returns the recorded result; incremental check/reference/invoke/output=0. New task or material question/context/decision/identity/revision/cutoff change creates a new packet and reruns. Label receipt/static/attestation evidence literally, never as OS event trace.

## Authority and return boundary

All outputs remain Game Design Candidates. Specialists own professional judgments; QA independently assesses evidence; Reviewer independently recommends; Owner alone decides adoption and proposed direction, transfer, threshold, tradeoff, promise, or quality bar. Nothing here authorizes implementation, production, scope/schedule, release, install, deploy, promote, or adopt. Return for Fresh QA, Reviewer, and explicit Owner decision without an adoption verdict.
