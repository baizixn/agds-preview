# Unity scene delivery

This is an assembly handoff procedure, not a verified Unity automation tool. Inspect the actual Unity version, render pipeline, enabled tools and target before choosing APIs or packages; consult matching official documentation for version-dependent operations. A missing connector is a tooling gap, not permission to invent successful editor actions.

1. Use an authorized isolated scene and asset subtree. Inspect existing hierarchy, prefab dependencies and scene settings before writing. Preserve unrelated scenes, project settings and importer changes; source-control presence and task authorization determine the workflow.
2. Establish units, root transforms and export axes with one representative asset before batch import. Measure actual renderer/collider bounds and contacts after import. An FBX/GLB file or an exporter success message is not an import receipt. If a format requires a missing importer, resolve that dependency explicitly rather than assuming support.
3. Keep reusable groups as Prefabs when useful, with stable readable hierarchy for terrain, architecture, vegetation, dressing and lighting. Do not create a framework for a one-off placement task. Preserve `.meta` identities and material references. Avoid text-editing unknown serialized formats where a supported editor route is available.
4. Run a small representative scene segment early: a structural join, a ground transition, a material under final lighting, and a dense vegetation patch when relevant. Check missing/pink materials, shader compatibility, scale, UV appearance, normals, contact and collision. Asset production and shader/system repair remain separately owned work.
5. Capture the reference cameras from the actual Unity scene. Persist explicit view identity, pose, projection mode, FOV/orthographic size, clipping, intended aspect and integer output dimensions. First capture and fresh reopen must restore the same contract; do not assume a runtime aspect assignment survives scene serialization. Bind the render target, restore the intended projection and record parameters/matrix actually used to render. Keep exposure, grading and preparation comparable; check actual images as well as parameter equality. Add the requested traversal with the actual runtime controller, including approach, interaction area and return; a Scene-view flythrough does not prove controller traversal or collision.
6. Profile requested target/build conditions with a supplied budget or an explicitly limited baseline comparison. Check measured frame time, memory, shadow/transparency/culling behavior as relevant. Successful Play Mode does not establish a player build, hardware performance or comfort.
7. Reopen the saved scene and verify references. Hand off the scene/Prefab entry path, dependency list, captures, controller/run instructions, revision identity and raw evidence. Label editor-only, Play Mode, standalone build and target-device evidence individually.

If Blender is used, keep its editable sources and export recipe linked to the imported revision. Blender renders support modeling/visual diagnosis; the requested Unity runtime appearance must be checked in Unity.
