## Default task entry

On an engineering request, follow this execution order in the existing task record:

1. Before editing, connect the approved behavior to its real entry, state owner, affected boundaries and finite completion checks. Decompose overall work into implementable tasks in dependency order; return missing product decisions to their owner instead of inventing rules.
2. For a first overall/cross-module implementation, or a material change to state ownership, shared interfaces or asynchronous/resource lifetime, read [working-method.md](references/working-method.md) and request an independent technical review before implementing the affected design. Route the request to the registered Reviewer, directly through supported delegation or through the orchestrator. Wait for its actual result and resolve in-scope blockers; an author checklist is not a review. A local leaf change and work within an unchanged reviewed design need no additional pre-implementation review.
3. Implement the reviewed responsibilities, including relevant rejection, cancellation, restart and cleanup paths. If evidence invalidates a decision, update it and route only the materially changed boundary for review.
4. Exercise the normal entry and relevant failure/lifecycle cases. For an authorized next-content change, compare the actual edit footprint with the expected extension point; otherwise report an inspection-based prediction, not demonstrated extensibility. Unrun levels remain unverified.
5. For material work or a task with an explicit independent-review requirement, request final review at a coherent delivery checkpoint with the actual source/diff and raw evidence, using the [review handoff](references/working-method.md#6-request-final-source-review). Retain its original output and finding disposition. Routine bounded repairs use proportionate self-checks and do not acquire an extra review chain. When independent review is required, do not declare it complete before the run finishes or substitute a design-only review for source review.

A low-risk local task can use a few sentences and its affected caller/regression check. Do not manufacture alternatives, research, module counts, a framework or a new Owner approval step. Engineering routes review; it does not assume the Reviewer's Skill authority. These are agent workflow obligations, not a tool-enforced write barrier. Respect task scope and pauses; this method does not authorize new experiments or unrequested features. Use [worked-examples.md](references/worked-examples.md) only for the matching boundary, pooling or asynchronous-cleanup question. The contracts below still apply.

## Engineering contracts

1. Read repository rules, the approved requirement, task stage, current version-control state, related implementation, direct and indirect callers, shared state and configuration, lifecycle boundaries, and current evidence. Start narrow, then expand the impact check when a shared boundary, dynamic callback, asynchronous path, network or resource lifetime, build dependency, unknown effect, or related external change appears. Do not read the whole repository or all history by default.
   - When a technical uncertainty could materially change feasibility or implementation cost, resolve the riskiest assumption with the smallest useful code inspection, authoritative reference, or executable probe. Check source version and applicability, tie the finding to a decision, and stop once the uncertainty is sufficiently reduced; routine changes need no research report.
   - When the user identifies an existing result below the requested bar, or an actual check shows a key problem remains, and no remedy has been verified for that problem, read and apply [task learning](../studio-orchestrator/references/task-learning.md) before further implementation. Reuse applicable verified experience first; when it is insufficient, inspect relevant experienced practice and first-hand process, compare alternatives and failure conditions, then choose a bounded probe under the current architecture, version, tools and authority. Keep the source, decision, attempt and check with the existing technical evidence; familiar small repairs with a verified remedy proceed directly.
2. Detect Git, SVN, or unmanaged filesystem status before using version-control commands. Never require or fabricate a commit for an unmanaged directory, and never initialize version control without owner instruction. Recheck relevant workspace state before editing and before handoff; if source, dependency, configuration, environment, or task input changed, invalidate stale analysis and evidence and reassess the affected scope.
3. Select the working mode from the task stage:
   - **Demo / Prototype:** deliver the smallest runnable, verifiable end-to-end slice quickly. Isolate temporary work, state its valid scope, technical debt, exit condition, and replacement path; keep logging, ownership, cleanup, and maintainability boundaries explicit.
   - **Production:** implement for long-term maintenance. When an existing implementation or Demo path exists, use evidence to choose one of `retain`, `harden_in_place`, `extract_refactor`, or `replace`, and record why the other choices are unnecessary or unsafe. For a greenfield Production task with no prior path, create the smallest maintainable new implementation that satisfies the approved requirement; do not invent an existing-path classification.
   - **Diagnosis / Fix / Hotfix:** trace the complete runtime chain and state ownership to the mechanism-level cause, then apply the narrowest fix. Do not include unrelated refactors or present rollback as the final mechanism-level solution.
   - **Refactor:** require evidence such as overloaded responsibility, duplicated facts, change amplification, testing difficulty, or performance risk. Establish observability and tests first, then preserve behavior through small slices. Stop at an Owner approval gate when architecture, migration risk, cost, or scope changes materially.
4. Keep state ownership, dependency direction, lifecycle, and the single source of truth explicit. Keep orchestration shallow and domain rules with their owner. Abstract only stable responsibilities, real variation points, platform or engine boundaries, and test seams. Prefer existing approved extension points; reject speculative frameworks, universal classes, meaningless wrappers, dynamic lookup without measurable benefit, and fragmented helpers without independent responsibility. Presentation may read game facts but must not own them.
5. Preserve existing boundaries and unrelated user changes. Do not modify unapproved product requirements, game direction, or another discipline's approved conclusions. Return cross-discipline discoveries as Candidate feedback.
6. Prefer the smallest reversible implementation that validates the approved requirement. When a Demo becomes Production, explicitly choose `retain`, `harden_in_place`, `extract_refactor`, or `replace`; check scale growth, blocking work, cleanup, streaming, batching, asynchronous needs, and the exit of temporary paths. Narrow legacy bypasses only after the approved replacement is stable.
   - For an approved Unity flat-plane articulated multi-leg locomotion slice, read `references/flat-multileg-locomotion.md` and use its explicit rig/configuration checks before considering the executable template. Keep this optional route within its supported rig and pose-ownership boundaries; it does not establish character modeling, animation fidelity, terrain adaptation, physical balance, or target-device readiness.
7. Make task-relevant performance acceptance explicit before implementation. Consider frame time, CPU, GPU, memory, loading, main-thread blocking, network, package size, power, and heat in proportion to the task. Never invent a cross-project number or claim a performance pass without a budget. If no budget exists, record a comparable baseline, require no obvious regression under the same device, scene, load, and build conditions, and mark the missing formal budget for confirmation.
8. Avoid obvious runtime traps even in a Demo: heavy per-frame allocation, full-scene scans, synchronous I/O, unbounded caches, listeners or timers, high-frequency network broadcasts, and unbounded logging. Sample, rate-limit, or disable high-frequency diagnostics. For production changes and refactors, compare before and after under equivalent conditions and report what was and was not measured.
9. Check cancellation, callbacks after object destruction or scene transition, event unsubscription, resource release, retry idempotency, partial failure, and state consistency when asynchronous or lifecycle behavior is relevant. Evaluate external engines, SDKs, plugins, runtime libraries, services, and platform configuration for performance, package, license, compatibility, build, and maintenance risk; stop for Owner approval if they change platform strategy or task scope.
10. Add observability and proportionate tests before claiming success. Use focused tests for feedback, then cover the affected subsystem and add regression, performance, build, runtime, or device validation according to risk. A local leaf change needs a light impact statement; a shared interface or medium/high-risk change needs an explicit impact list and all callers checked.
11. Report `implemented`, `static_or_local_verified`, `runtime_verified`, `device_or_player_verified`, and `performance_verified` separately. A missing level remains `not_verified`; do not infer it from another level. Report the technical decision, impact scope, test and performance evidence, risks, temporary-path exit conditions, and unresolved questions.
   - Consider the people configuring, using, debugging, and changing the result when choosing an implementation. Remove observed friction in proportion to its cost; add tools or abstractions only for a concrete need. Leave the smallest useful handoff: how to run or use it, where intended changes belong, key tradeoffs, and how to reproduce or diagnose relevant failures.
12. Self-review for regressions, performance, maintainability, hidden scope growth, stale evidence, unapproved requirement changes, and project-fact contamination. For material work or an explicit task review requirement, submit a minimum Candidate packet to an independent Reviewer at a coherent delivery checkpoint. Routine bounded repairs retain proportionate checks without a mandatory extra review chain; Reviewer advice is not Project Owner approval.


## Optional Unity static-asset receipt tool

For a task that needs read-only acceptance of already imported static FBX/Prefab assets, engineering may use [the Unity static-asset receiver](references/unity-static-asset-receiver.md). Obtain the project-specific dimensions, trusted direction-marker contract, material expectations and tolerances first; do not infer expected values from measurements or silently rebind changed inputs. The tool reports missing/unsupported evidence explicitly and never repairs assets. This is an on-demand helper, not a required step for ordinary engineering, unrelated tasks, or other engines. Validated scope: Unity 6000.5.10f1 + URP 17.5.0, Linear, static MeshRenderer hierarchies and three declared URP Lit properties.
