# Experience Contract

Use this compact template only when the approved task establishes or materially refreshes the primary player experience. Keep it to one page when practical. Do not turn it into a feature list or duplicate an already approved equivalent. In Owner-authorized formation mode, label the contract and every proposed player promise or quality bar as Candidate until the Owner decides it.

Populate the fields only from routed, approved directional inputs. If any required directional input is missing, return a compact missing-input record naming the absent input and stop; do not infer, invent, or complete the remaining contract fields from a feature list or plausible project context.

| Field | Required content |
| --- | --- |
| Target player | Who the experience is for and the relevant assumed familiarity. |
| Use context | Platform or setting, input context, intended session shape, and material constraints. |
| Core feeling | One plain-language player promise that the work is trying to make true. |
| Observable behaviors | A small set of behaviors expected when the promise is working. |
| Falsifiers | Concrete observations that would show the promise is not working. |
| Quality floor | The minimum readability, responsiveness, feedback, accessibility, comfort, or other approved qualities that may not be traded away at this stage. |
| Explicit exclusions | Attractive but out-of-scope work that must remain deferred. |
| Validation methods | Which claims automation or expert inspection can address, which require human/player evidence, the target artifact, environment, and decision rule. |

Every behavioral claim must remain falsifiable. Missing human evidence stays `Not Run` or `Inconclusive`; a planned playtest is not observed evidence. Direction, target-player, platform, quality-floor, or scope changes remain Project Owner gates.

## Experience Quality addendum

Use only the fields material to the current stage and uncertainty; this is not a universal checklist or scorecard.

| Field | Required content |
| --- | --- |
| Contract identity | Stable identity, state, approved baseline or supersedes relation, and evidence cutoff. |
| Stage quality profile | Current stage, decision question, what must already work, what may remain rough, and what is explicitly not being judged yet. |
| Material quality dimensions | Only the experience dimensions that can change the current decision; for each, the intended player perception or behavior, why it matters now, responsible content owner, and falsifier. |
| Reference calibration | Source and evidence status, the abstract experience property to learn, contextual difference, transfer assumption, rights or protected-expression boundary, and what must be transformed rather than copied. Popularity is not evidence of fit. |
| Anti-reference calibration | The experience property to avoid, its expected player consequence, the current risk it illustrates, and the same source and expression boundaries. |
| Professional contributions | Responsible Design, Art, Audio, UI, Engineering, QA, or other approved owner; intended player-side effect; domain success and failure conditions; artifact/context; evidence class; and current owner-supplied state. |
| Cross-discipline coherence | Only evidence-linked claims about how information, emotion, feedback, pacing, and recovery reinforce or conflict with one another. Preserve disagreement as `Inconclusive`. |
| Allowed tradeoffs | Project-specific acceptable tradeoffs, unacceptable costs, and the boundary that requires Owner direction or quality-bar approval. |
| Current assessment | `Not Run`, `Inconclusive`, `Supports`, or `Falsifies`, with artifact/build identity, environment, evidence cutoff, limits, gaps, and unresolved conflicts. This is an experience-hypothesis assessment, not a QA Pass or universal score. |
| Refresh triggers | Material contract change, first playable or approved checkpoint, professional contribution change, evidence invalidation, contradiction, target-player falsifier, or Owner request. |
| Unresolved questions | Question, responsible owner, required evidence, decision deadline or gate, and `owner_decision: not_decided`. |

## Actionable critique record

Each material critique must identify the contract and promise, target artifact/version and gameplay context, evidence identity/class/limits, observed player impact, gap, provisional root-cause hypothesis and credible alternate explanation, smallest discriminating experiment, falsifier, implementation owner, validation owner, final decision owner, and recheck trigger. A statement such as “make it more premium,” “more fun,” or “more like the reference” is not actionable unless the record supplies those bindings.

Expert critique can support a professional assessment. It cannot replace target-player, affected-player, real-device, comfort, usability, accessibility, or listening evidence when the approved claim requires that evidence.
